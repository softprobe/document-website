# 核心功能与性能参数

> 本说明面向系统使用方和决策方，回答四个问题：系统能做什么、能做到多大规模、处理有多快、需要占用多少资源。文中性能数字均来自系统现有代码、配置和设计文档，实测数据单独标注。

![SoftProbe 系统架构图](/img/docs/data-flow.png)

---

## 一、系统是做什么的

SoftProbe 是一套流量录制回放测试平台。它的工作方式是：把线上真实请求连同其调用的数据库、缓存、下游服务一起"录"下来，之后在版本升级、系统改造或新环境验证时，把这些真实流量"回放"一遍，并自动比对两次结果，找出不一致的地方。

它解决的是两个常见问题：

1. **测试覆盖不足**：手工编写的测试用例，很难覆盖线上真实出现的各种参数组合和边界场景。
2. **回归靠人肉**：系统升级后，往往要人工对比新旧结果才能发现哪些接口行为变了。

用真实流量替代人工构造的用例，是这套系统的核心价值。

## 二、核心功能（能做什么）

### 1. 流量录制（无需改业务代码）

在被测应用的 JVM 启动参数里加一行探针，即可开始录制，不需要修改任何业务代码，也不需要在代码里埋点。

录制时，系统自动抓取两类数据：

- **入口流量**：HTTP 接口、Dubbo 服务、消息消费等入口的完整请求和响应。
- **出站依赖**：应用调用数据库、Redis、HTTP 下游、RPC 服务时的完整请求参数和返回结果。

这意味着录下来的不只是"接口返回了什么"，还包括"这个接口内部查了哪些数据、调了哪些服务、各拿到什么结果"，形成一条完整调用链。

**已支持的框架范围**（覆盖主流 Java 技术栈）：

| 类别 | 支持范围 |
|---|---|
| 应用入口 | Servlet、Spring Boot、Spring Cloud Gateway、Dubbo Provider、Netty |
| HTTP 客户端 | Apache HttpClient、OkHttp、Feign、RestTemplate、WebClient |
| 数据库 | MyBatis、MyBatis-Plus、Hibernate、MongoDB |
| 缓存 | Jedis、Lettuce、Redisson、Spring Data Redis、Caffeine、Guava |
| RPC | Apache Dubbo / Alibaba Dubbo |
| 其他 | Apollo 配置中心、线程池、系统时间、Spring Security / Shiro 等 |

### 2. 流量回放（无需真实依赖环境）

回放时，系统用录制好的数据"顶替"外部依赖：数据库查询直接返回录制时的结果，下游服务调用直接返回录制时的响应，不再访问真实数据库和真实下游。

好处是：

- 回放不需要准备一套完整的测试环境（数据库、依赖服务都能省掉）。
- 可以对线上流量反复、批量地重放，做压力验证或回归验证。

### 3. 结果自动比对

对"录制结果"和"回放结果"做字段级别的逐项比对，自动忽略时间戳、UUID、随机数、IP 地址这类每次都变、但没有业务意义的值。

比对结果分为：一致、有差异、回放多调用了、回放少调用了等几种情况，并把差异定位到具体接口和具体字段。

### 4. 回放报告与问题定位

每次回放生成报告，展示通过率、失败项、差异明细，并可按日查看趋势。有差异的用例能直接跳到对应接口，看到新旧两份报文的具体差别。

### 5. 敏感数据保护

对录制数据中的敏感字段（身份证号、手机号、银行卡号等）提供两道保护：

- **展示打码**：在查看页面把敏感字段脱敏显示。
- **字段加密**：落库时对敏感字段加密存储，支持 AES-256 和国密 SM4 算法。

### 6. 回放失败诊断

回放出现差异或失败时，系统可以自动抓取该用例的请求、响应、依赖调用和日志，比对后给出根因判断，减少人工排查工作。

### 7. 管理与协作

提供 Web 工作台，支持应用管理、回放计划管理、录制/回放策略配置（可导入导出）、用户与权限管理、报告看板等功能。

## 三、性能与规模（能做多少、多快）

### 1. 探针对业务系统的影响（重点）

探针是挂在被测应用内部的，客户最关心它对业务性能的损耗。结论如下：

| 关注点 | 结论 |
|---|---|
| 挂载方式 | JVM 启动加一行参数，不改代码 |
| 常规负载下的损耗 | 万级 QPS 的普通业务无感；被录制的接口单次额外开销在微秒到几十毫秒量级 |
| 额外占用线程 | 约 10～20 个后台线程（以守护线程为主），独立于业务线程池，不抢占业务线程 |
| 数据上报 | 异步批量上报，不阻塞业务请求 |
| 保护机制 | 宿主 CPU / 内存超过阈值时自动降速；缓冲写满自动丢弃，不影响业务 |

需要说明的一点：上述"微秒到几十毫秒"是普通报文的开销。如果单次请求/响应达到几十 MB 的大报文，序列化本身会带来明显开销，这类场景需要在接入时做针对性调优（限制录制报文大小、调整采样率等）。系统已内置报文截断保护（网关入口请求 1MB、响应 10MB 封顶）。

### 2. 录制吞吐

| 指标 | 数值 | 说明 |
|---|---|---|
| 单条录制数据落库耗时 | 约 2 毫秒 | 后端入库单条处理耗时（设计基线） |
| 后端入库能力 | 约 400 QPS | 单条写入的设计处理能力 |
| 探针侧采样 | 可配置 | 默认约 1000 条/秒，可按需调整采样率 |

录制数据在探针侧先进入内存缓冲，攒批（约 50～200 条一批）后异步上报，避免频繁网络请求。

### 3. 回放吞吐

| 指标 | 数值 | 说明 |
|---|---|---|
| 回放压力 | 可配置 | 默认 20 QPS/实例，支持 0.25 倍到 8 倍调速 |
| 实时回放处理 | 约 1 秒/批 | 每批约 800 条用例的处理耗时（8 核、分片预热场景） |

回放压力是受控的：系统按阶梯逐步加压，连续成功才升档，失败自动降档，避免把目标系统打垮。

### 4. 规模上限（能做到多大）

系统已在以下规模场景下验证和评估过：

- **百万级 QPS 网关场景**：接入 Spring Cloud Gateway，处理大报文（请求约 1MB、响应约 10MB）。该量级下需要在接入时完成探针参数调优（主要是缩短内部上下文的保留时间、限制录制采样），调优后可平稳运行。
- **海量数据**：按 50 万条/秒、单条约 5KB 估算，数据写入约 2.5GB/秒，约 216TB/天；存储层基于 MongoDB 分片，可水平扩展。

存储层设计上，后端只需 MongoDB 和 Redis 两类基础设施，其中 MongoDB 承担持久化，Redis 承担回放期间的高速缓存，均可通过分片/集群方式扩展。

## 四、资源需求（需要多少资源）

### 1. 探针侧：几乎零额外资源

探针运行在被测应用自己的 JVM 里，不需要独立服务器。额外占用为：

- 约 10～20 个后台线程（多数为守护线程，空闲时几乎不耗 CPU）。
- 少量内存用于缓冲和类增强（Metaspace）。

探针的数据上报走自己独立的连接池，不与业务线程池、业务连接池混用。

### 2. 后端：一台普通规格服务器即可起步

后端提供 All-in-One 单体部署形态，把配置、存储、调度、报告等能力合并为一个进程，单端口对外。默认 JVM 内存配置 2GB 起步、最大 3GB。

| 组件 | 资源规格 |
|---|---|
| 后端单体（All-in-One） | 内存 2GB～3GB，无需多台机器 |
| 数据库 | MongoDB（持久化存储） |
| 缓存 | Redis（回放期间高速缓存） |

系统不依赖消息队列、对象存储等额外组件，部署依赖极少。

### 3. 部署形态

交付版共 4 个容器：后端、前端控制台、MongoDB、Redis，通过 Docker Compose 即可一键拉起。

## 五、接入方式（多快能用上）

1. **接入探针**：在被测应用启动命令加一行 `-javaagent` 参数，指向探针 jar，并配置后端地址，即可开始录制。全程不改业务代码。
2. **部署后端**：Docker 一键部署后端与前端控制台。
3. **开始使用**：在工作台创建应用，录制流量，创建回放计划，查看比对报告。

从部署到录到第一批流量，通常当天即可完成。

---

## 六、几点如实说明

- 探针挂载不会引入代码改动，但字节码增强属于 JVM 层面的技术手段，个别与既有字节码增强类组件（如其他 APM/录制类 agent）并存的环境，建议先行评估兼容性。
- 普通报文、万级 QPS 场景下探针损耗可忽略；超大报文、百万级 QPS 场景需要按接入指南调优后使用。
- 回放依赖后端稳定运行，建议回放与后端的网络、存储保持健康状态。
