# CI/CD 发版回归

每次发版前，新版本都要回归一遍，确认改动没改坏已有行为。这一页讲两件事：怎么用回放做这次回归，怎么用回归结论决定发不发布。推荐接进 CI/CD 流水线自动做，各家 CI 脚本现成（见 [发版后自动回放](/zh/testing/webhook-and-ci)）。

生产环境的服务挂上 SoftProbe 的 Agent（随服务启动的探针程序），把线上真实的请求和处理结果录下来。每次发版，新版本先部署到测试环境，流水线把录下的请求重发给新版本；新版本照常跑业务代码，要查数据库、调下游服务时，由录下的结果应答。最后对比新版本和线上的结果，给出结论，流水线按结论决定继续发布还是停下。原理详见 [流量回放测试](/zh/testing/)。

## 回归做不好，只有两种结果 {#two-failures}

- **漏掉真问题**：真问题没被发现，跟着发布上了线。
- **误报多到没人看**：无关的差异报得太多，大家习惯性地放行，回归照跑，却没人再看。

第二种更常见，也更难察觉：回归很少被停掉，多半是被无视的。下面每条做法都对着其中一种。

## 让回归发现真问题 {#catch}

### 只拿生产录下的请求当标准 {#prod-baseline}

**做法**：录制时给生产环境的请求打上环境标签（如 `env=prod`），回放时只筛这部分请求。测试环境的服务也挂 Agent、用同一个应用 ID，但不录制，只接受回放。

**为什么**：回放回答的是「新版本和线上比，变没变」，比对的标准只能是线上的真实表现。测试环境录下的请求混进来，标准就不纯了；回放发出的请求要是又被录下来，下次等于自己和自己比。

**不这样**：报告里混着测试环境带来的差异，每次发版都要先分辨哪些算数。

::: warning 测试环境必须和生产隔离
回放时，数据库、缓存、下游接口的调用默认用录下的结果应答，找不到对应结果时判为失败。但应用可以把个别依赖设成真实调用，少数类型的调用（例如 UMQ 消息发送）找不到录制时也会真的发出去。所以测试环境不能连生产的数据库和下游服务。另外，触发回放的接口没有鉴权，只能让内网的 CI 机器访问。详见 [依赖 Mock](/zh/testing/policies#mock) 和 [准备工作](/zh/testing/webhook-and-ci#before-you-start)。
:::

### 用一张必测清单定义「测够了」 {#must-test}

**做法**：把每次发版必须测到的接口列成清单，产品里叫「主链路接口」。清单按业务风险定，不能为了让检查通过而删掉没测到的关键接口。只在月底、夜间才有的关键请求，可能不在最近一天的录制里，把它们另存为「固化用例」（不会随录制过期删除），发版时和最近的录制分别回放、分别看结论。

**为什么**：「测够了没有」是业务判断，只能由人来定。没有清单时，系统只能按数量兜底：一次回放测到的接口不到 10 个、或请求不到 30 个，即使全部通过也判「覆盖不足」。有了清单，改为检查清单里的接口是否都测到了。

**不这样**：某个关键接口这次恰好没录到，其他接口又都通过，回归照样通过。不是没拦住，是根本没测。

登记方法见 [主链路接口](/zh/testing/webhook-and-ci#main-operations)，固化方法见 [固化用例](/zh/testing/pinned-cases)。

### 只认结论，不看通过率；没测成也要停 {#only-clean}

**做法**：回放结束后，系统给出一个结论（查询接口里的 `findings.state` 字段），流水线只按它决定：

| 结论 | 意思 | 流水线 |
|---|---|---|
| `CLEAN` | 测了，没发现问题 | 唯一可以自动继续发布的情况 |
| `NEEDS_ACTION`、`REVIEW_ONLY` | 结果有变化，例如接口报错、字段值变了、多了字段 | 停下，由人看报告确认 |
| `LOW_COVERAGE`、`NO_CASES`、`INTERRUPTED`、`ENVIRONMENT_FAILURE` | 这次没测成：覆盖不足、没有可回放的请求、没跑完、大量接口同样报错 | 停下，查清原因重跑 |

**为什么**：通过率 95%，可能恰好是下单接口坏了；通过率 100%，也可能只测了三个接口。「没测成」最容易被当成「没问题」，可它恰恰是回归什么也没测到的时候。代价是偶尔多停几次。

群通知只是让人及时知道结果，可能晚到、也可能发送失败，不能当放行依据。脚本见 [完整脚本](/zh/testing/webhook-and-ci#script)，各结论的判定条件见 [根据结论决定是否继续](/zh/testing/webhook-and-ci#decide)。

## 让回归不误报、不被绕开 {#trust}

### 用回归结论拦发布之前，先验证回归本身靠得住 {#before-gating}

**做法**：正式拦发布前做三件事：

1. **同一个版本先跑干净**：把线上正在运行的同一个版本部署到测试环境，回放一次。这时代码没变，报出的差异都是噪音。时间戳、随机 ID 这类每次都变的字段，确认不影响业务后配成对比规则，以后比对时跳过；测试环境配置不同造成的，先把环境调齐。反复跑，直到结论是 `CLEAN`。
2. **故意改坏一次**：改一处会影响返回结果的代码，确认流水线真的会停。
3. **拿不准就先观察**：先让回放只出结论、不拦发布，跟几次真实发版跑下来，结论稳定了再正式拦。

**为什么**：第 1 步证明「代码没变时它不乱报」，之后报出的差异才值得打开看；第 2 步证明「代码变了，流水线真的会停」，排除脚本没接对、报了问题流水线却照走的情况。

**不这样**：带着噪音上线，每次发版都被同样的差异拦下，几次之后就没人再看报告了。

对比规则的配法见 [对比规则](/zh/testing/compare-rules-web-ui)。

### 结果变了由人确认，业务字段不能加进忽略规则 {#human-decides}

**做法**：流水线因为结果有变化停下时，由开发或测试打开报告逐处确认：

- 不是预期的变化：修好，重新发版。
- 是这次有意的改动：在报告里点「标记通过」，再在流水线里人工放行。「标记通过」只对这一次回放有效。
- 确实不影响业务的字段：配成对比规则，以后不再比。

**为什么**：回放比的是「和线上一不一样」，不是「对不对」。线上本来有 bug、新版本修好了，回放也会报差异。「变没变」由系统报，「该不该变」只能由人判断。

**不这样**：为了让流水线通过，把金额、状态这类业务字段加进忽略规则。从此，这个字段怎么变回归都测不到，而流水线看起来一切正常。

逐处确认的方法见 [审查差异](/zh/testing/review-diffs-in-the-web-ui)。

### AI 帮忙查原因，不替人决定放行 {#ai}

**做法**：接入 AI 后自动做两件事。一是「降噪」：把时间戳、随机 ID 这类每次都变的字段识别出来，这次回放不再比；金额、状态这类业务字段不会被自动忽略。二是「查原因」：把没通过的用例分成「代码改动引起」「原因未查明」「无效」三类，查到代码改动的会说明改了什么，定位到时给出文件和行号。流水线等降噪做完再出结论，但不等查原因；查原因的结果也不改变结论。

**为什么**：AI 也会判错，所以放不放行始终由人决定；它省掉的是人一条条翻用例找原因的工夫。另外，AI 读的是代码仓库里绑定分支上的代码，不会核对它是不是这次发布的版本。绑定的分支要和发版分支一致，看归因前先看一眼报告里注明的分支和提交。

配置见 [配置 AI 诊断与代码仓库](/zh/testing/installation/ai-diagnosis)。

### 定期回头看 {#review-regularly}

**做法**：定期看两样东西：报告里标着「已连续 N 次」的差异，和对比规则里忽略了哪些字段。

**为什么**：有意的改动上线后，线上旧版本录下的请求还在回放范围内时（默认回放最近 24 小时的录制），之后的发版会重复报出同一处差异，每次仍要确认它还是同一处变化。忽略规则只会越加越多，时间长了难免混进业务字段。

**不这样**：回归一直全绿，却分不清是真的稳，还是问题都被规则挡掉了。

## 照这些做法跑一次（演示环境） {#example}

下面是一次真实运行，环境是演示用的：一个 Java 计价服务，3 个接口都登记为主链路接口；生产和测试实例在同一台机器，线上流量由脚本模拟；对比规则里已排除每次都变的 `quoteId`、`quotedAt`。

1. 开发提交了 `0026097`「调整会员价计算」，把会员价的取整从四舍五入改成了向下取整。
2. 新版本部署到测试环境，流水线回放了线上最近 1 小时录下的 237 个请求，约 2 分钟后得到结论 `NEEDS_ACTION`，流水线停下。
3. 报告显示：`/order/price` 回放的 81 个请求里，79 个的应付金额 `payable` 比线上少 1。这 79 处差异都来自同一处改动，没有需要分辨的噪音。
4. 流水线停下约 10 分钟后，AI 查完原因：79 条都是代码改动引起，定位到提交 `0026097` 和 `PricingService.java` 第 12 行，通知随即发出。
5. 开发确认这不是有意的改动，改回四舍五入重新发版。这时代码和线上一致，结论是 `CLEAN`，流水线继续发布。

![演示环境的回放报告：79 处差异由代码改动引起，定位到提交和代码行](/img/docs/testing/zh/cicd-report.png)

截图说明：顶部的 `openapi-sp-diag-e2e-app-128` 是这次回放的计划名，带着演示应用的 ID 和流水线编号；差异旁的「已连续 10 次」，是因为演示环境此前用同一个改动跑过多次。

这次能测出问题，靠的正是前面几条：金额字段没有被忽略，所以变化被发现；只认结论，所以 `NEEDS_ACTION` 一出就停；原因由 AI 查，放不放行由人定。

## 落地自检 {#checklist}

| 检查项 | 合格标准 | 去哪做 |
|---|---|---|
| 生产录制打标签 | 生产的请求带 `env=prod` 这类标签 | [接入 Java Agent](/zh/testing/java-agent) |
| 测试环境不录制 | 测试环境的采样率设为 0 | [录制配置](/zh/testing/policies#recording) |
| 回放只用生产的请求 | 触发回放时按标签筛选 | [触发回放](/zh/testing/webhook-and-ci#trigger) |
| 测试环境与生产隔离 | 不连生产的数据库和下游；触发接口只对内网 CI 开放 | [准备工作](/zh/testing/webhook-and-ci#before-you-start) |
| 必测清单 | 必测接口都已登记；低频关键请求已固化 | [主链路接口](/zh/testing/webhook-and-ci#main-operations)、[固化用例](/zh/testing/pinned-cases) |
| 先验证靠得住 | 同一版本回放到 `CLEAN`；故意改坏一次，流水线会停 | [对比规则](/zh/testing/compare-rules-web-ui) |
| 流水线只认结论 | 只有 `CLEAN` 自动继续，没测成也停 | [完整脚本](/zh/testing/webhook-and-ci#script) |
| 有人负责确认 | 谁看报告、谁能人工放行，事先约定好 | [审查差异](/zh/testing/review-diffs-in-the-web-ui) |
| AI（建议） | 模型已接入，绑定的是发版分支 | [配置 AI 诊断与代码仓库](/zh/testing/installation/ai-diagnosis) |
| 通知 | 群机器人测试发送成功 | [回放结果通知](/zh/testing/notifications) |
