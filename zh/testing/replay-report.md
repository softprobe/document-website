# 回放报告

每次回放结束后，Softprobe 会生成一份回放报告。报告自上而下回答三个问题：要不要管（第一行是结论）；要管什么、为什么、怎么办（「问题」区的卡片）；其余未通过的用例是怎么回事（「原因未查明」「其他结果」和底部的「回放设置与统计」）。本页也按这个顺序讲。

录制、回放和对比的基本概念见 [工作原理](/zh/testing/how-it-works)；逐条查看差异、忽略字段、标记通过的方法，详见 [审查差异](/zh/testing/review-diffs-in-the-web-ui)。

## 打开报告 {#open-report}

在应用工作台左侧选择「回放」→「执行记录」，点击一条记录，再切到「报告」页签。旁边的「用例列表」页签是这次回放的全部用例。

由流水线（CI）触发的回放，可以直接通过接口返回的 `reportUrl` 或群通知中的按钮打开报告，详见 [发版后自动回放](/zh/testing/webhook-and-ci)。

页面头部是这次回放的总览：

- **结果标签**：分析完成时显示「代码改动 · N 个问题」「原因未查明 · N 条」或「未发现代码改动引起的问题」；还没有分析结果时按回放结果显示「通过」「未通过 · N 条」「回放没跑成」等。
- **「用时」「通过率」** 和用例结果条。通过率 = 通过 ÷（通过 + 有差异 + 回放失败），本例即 33 ÷ 50 = 66%。每条用例是三种结果之一：**通过**、**有差异**（回放跑成了，但返回或调用与录制时不一致）、**回放失败**（没跑出可比对的结果）；后两种合称「未通过」。
- **「回放参数」和「再次回放」**：「回放参数」回看这次回放创建时填的参数（只读）；「再次回放」按同样的参数再跑一次——点开是以这次参数预填的新建回放，确认后创建一次新的回放，生成新的一份报告（这次回放还在进行时不可点）。改完代码后用它重跑。
- **「导出」和「问 AI」**：导出见 [导出报告](#export-report)。「问 AI」打开这次回放的对话，AI 看得到这次回放和分析的进度与结论，可以接着提问。

![回放报告的页头、结论和第一个问题](/img/docs/testing/zh/report-overview.png)

## 结论 {#verdict}

生成报告分三步：**回放**、**AI 降噪**、**AI 分析原因**。AI 降噪识别时间戳、随机 ID 等每次都会变化的字段，有把握的自动忽略，把握不足的留作「疑似噪音」由人工勾选；AI 分析原因再查仍未通过的用例，判断差异是不是代码改动引起的。流水线触发的回放默认自动完成这两步；手工回放默认只自动降噪，原因分析在报告中手动开始；定时回放暂不支持自动分析，同样在报告中手动开始。这些默认行为在 [流程设置](#flow-settings) 里调整。

报告第一行是结论主句，内容随回放和分析的进度变化：

| 情形 | 主句示例 |
|---|---|
| 分析完成，查出问题 | 2 个问题由代码改动引起，需开发确认是否符合预期，另有 1 条用例原因未查明 |
| 分析完成，没有代码引起的问题 | 本次回放未测出代码改动引起的问题 |
| 问题已全部人工确认 | 2 个问题已由人工确认符合预期 |
| 分析中 | AI 正在分析原因，结论还在更新 |
| 分析没做完 | 目前查出 2 个问题由代码改动引起，需开发确认是否符合预期 |
| 分析没开始 | 原因分析未进行：今日自动分析次数已用完 ／ 尚未分析原因 |
| 没有 AI 分析（Softprobe 服务端版本较旧） | 17 条用例未通过，5 类差异待确认 |
| 全部通过 | 50 条用例全部通过 |
| 回放没跑完或没跑成 | 回放进行中 ／ 回放没有跑完 ／ 回放没跑成：回放被中断 ／ 回放没跑成：回放被取消 ／ 没有可回放的请求 |

「回放没有跑完」是出了一部分结果，已回放的照常可看；「回放没跑成」是整次被中断、被取消，或没有可回放的请求。

主句下面的第二行随情形变化：

- 分析完成时，把未通过的条数按去向拆开，例如「共 50 条用例：33 通过 · 17 未通过；未通过中 13 条由代码改动引起（见「问题」）、3 条见「其他结果」」——加上主句里说过的 1 条原因未查明，正好是 17 条。
- 还没有分析结果时，只写加总，例如「50 条用例：33 条通过，17 条未通过」；有忽略噪音后才通过的用例时，在通过数后注明，如「33 条通过（其中 15 条是忽略噪音后通过的）」。
- 标记通过之后，多出一行处理进度，如「已确认 1 个问题（11 条标记通过），还有 1 个问题待确认（2 条）」。结论里的这些数字不变：它们说的是回放跑出来的结果（含 AI 降噪后转为通过的），不随人工确认改变；变的只有主句的措辞和这一行处理进度（页面头部的通过率和结果条同样按它）。

分析没做完时，主句下方出现黄条，如「AI 分析原因没有做完（今日自动分析次数已用完），还有 3 条没分析，结论不完整」，可点条上的「重新分析」。还没分析时，结论旁有「分析本次回放」；三步各自的状态和手动入口也在 [回放设置与统计](#replay-info) 里。还没分析到的用例，不等于没有问题。

报告页尾注明「原因和处理方法由 AI 给出，经 AI 核对，未经人工确认。」，行尾的「重新分析」可让 AI 重查一次。

::: warning 结论不等于可以发版
「本次回放未测出代码改动引起的问题」不等于没有差异：「原因未查明」的用例仍需人工排查，AI 的判断也可能出错。是否发版始终由人决定。
:::

## 问题 {#problems}

有 AI 分析结果时，未通过的用例按三档列出：**问题**（由代码改动引起，需开发确认）、**原因未查明**、**其他结果**。这一节讲第一档，后两档见 [原因未查明与其他结果](#other-tiers)。「问题」这一档在页头结果标签、用例抽屉标题和导出文件里写作「代码改动」；标题行右侧的「按原因 / 按差异」切换见 [按差异查看](#by-diff)。

每个问题一张卡片，从上到下是：

- **编号和标题**：一句话概括改动，如「会员价改为向下取整，应付少 1 元」。标题旁的标签：「AI 核对通过」表示这条结论经过复核：代码改动与差异对得上；「AI 推断，未核实」表示结论是 AI 推断的，还没有核对代码，只能当作排查线索；「AI 判断为代码缺陷」表示 AI 判断这是缺陷、需要修正代码（没有这一标签的，按预期改动确认处理）；「含并入的 N 个问题」表示另有 N 个问题被 AI 判断原因相同、并进了这一个问题。
- **影响**：如「影响 11 条用例（共回放 36 条）」——「共回放」是涉及的接口这次回放条数的合计（/order/price 22 条加 /order/detail 14 条），不是整次回放的总数。名下有用例回放失败时，单独标明「1 条用例回放失败，没有可比对的结果」：AI 判断这些失败同样由这处改动引起。
- **依据**：涉及接口、代码位置、改动提交，以及变化涉及的字段数和路径数——「路径」按取值变化分行：同一个字段变出几种取值，就算几条（本例 payable 一个字段、4 种取值变化，即「1 个字段 · 4 条路径」）。点「查看代码改动」就地展开改动前后的代码；点「查看 AI 分析过程」看 AI 得出这条结论的过程。
- **处理方法**：「开发确认符合预期后，由有权限的使用者标记通过；否则开发修正代码后重新回放。」（「有权限的使用者」的口径见 [处理一个问题](#handle-a-problem)。）名下用例全部是回放失败时，没有结果可确认，处理方法改为「修复代码后重新回放。」，卡片上也不再有「标记通过」。
- **操作**：「标记通过（N 条用例）」「复制问题」「查看 N 条用例」。带「AI 判断为代码缺陷」标签的卡片上「标记通过」仍在，但不再是高亮的主按钮。

代码证据有几种情况，卡片上分别注明：

- 应用绑定了代码仓库、取到了改动：依据行显示代码位置和改动提交，「查看代码改动」展开改动前后的代码；定位到代码但没取到提交时，注明「代码位置已定位，没有取到最后改动这一行的提交。」
- 没有绑定代码仓库，但 Agent 上传了运行时加载的程序包：照常给出代码块，标题是「录制时运行的代码 → 回放时运行的代码」，并注明代码取自程序包、没有注释，变量名可能与源代码不一致。
- 代码仓库和程序包都没有，或读到了代码却没能定位：注明「分析时没有读到代码仓库，看不到改动的代码和提交，原因是按返回数据推断的」或「分析没有定位到改动的代码，原因是按返回数据推断的」。可点「去绑定代码仓库」，绑定后重新分析；绑定方法见 [配置 AI 诊断与代码仓库](/zh/testing/installation/ai-diagnosis)。

### 处理一个问题 {#handle-a-problem}

一个问题的处理闭环是：开发确认改动是否符合预期——符合，「标记通过」；不符合，开发修正代码后重新回放。

「有权限的使用者」没有单独的角色配置：能登录并打开这个应用的使用者都可以点「标记通过」，开发自己登录后也可以。唯一不能点的是未登录的匿名只读访问，这时所有写操作的按钮都是锁住的。

**标记通过**：点「标记通过（N 条用例）」，这些用例的结果随即改为通过，卡片上出现「已标记通过 N 条」和「撤销」；全部标记后卡片收成一行。所有问题都确认、且没有原因未查明的用例时，结论变为「N 个问题已由人工确认符合预期」。标记只影响本次回放，随时可撤销。

「标记通过（N 条用例）」一次标记这个问题名下的全部用例，只有一种例外：并入的问题里回放失败的那几条不带——它们没有可比对的结果，无法成批确认，要在抽屉里逐条查看、确认后再标记。卡片会注明「其余 N 条可在右侧用例列表中单条标记」：这里的「用例列表」指「查看 N 条用例」打开的右侧抽屉，不是「用例列表」页签。

这处问题名下的字段里，可能混着与改动无关、每次都变的噪音字段。如果 AI 降噪建议忽略其中某个字段、而它还没被忽略，主按钮会变成「标记通过并忽略 &lt;字段&gt;（N 条）」，旁边保留「仅标记通过」。它把标记和忽略一次做完，确认框里选两项：

- **忽略期限**：「只这次回放」，或「以后每次回放都忽略」；
- **适用范围**：「这个应用的所有接口」，或「只 /order/price」（只当前接口）。期限选「只这次回放」时，范围固定为这次回放的所有接口——只对这次生效的忽略不能单独限定接口。

忽略只是写好规则：同一字段上其他用例的差异要 [重新对比](/zh/testing/review-diffs-in-the-web-ui#recompare) 后才不再报。

**复制问题**：复制一段整理好的文字——标题、归因、涉及接口、代码位置和提交、涉及用例数、取值变化、处理方法和报告链接，贴到工单或群聊，转给开发确认。

**查看 N 条用例**：在右侧抽屉里看这个问题名下的全部用例，按返回结果怎么变的分组（取值变化相同的用例在一组），可以按用例编号或取值搜索；点一条看逐字段对比和调用链，也可以单条标记通过；抽屉底部同样有整组的「标记通过（N 条用例）」和「复制问题」。

![「查看 N 条用例」的抽屉](/img/docs/testing/zh/report-drawer.png)

问题超过 3 个时，卡片左侧出现勾选框，可勾选几个后批量复制、批量标记通过；如果这些问题还涉及不止一个接口，「问题（N）」那一行会再出现接口筛选。

### 问题详情 {#problem-detail}

卡片底部的「问题详情」默认收起，展开后包括：

- **原因**：AI 结合一组具体数据，解释差异是怎么产生的。
- **返回结果的变化**：按取值变化分组，一组一行，列出字段、录制时的值、回放时的值和涉及的用例数；超过 6 组时折叠，点开看全部。
- **回放结果**：名下回放失败的用例，按报错类别列出。
- **并入的问题**：AI 判断原因相同、并入这一问题的其他结论各占一行，写明它原来影响的用例数和核对状态（「AI 核对通过」或「AI 推断，未核实」）；原来的归类与这一问题不同的，还会注明「原归类：××」。「AI 的归并理由」可展开。这些用例已计入卡片的影响数。

![展开的问题卡片：代码改动和问题详情](/img/docs/testing/zh/report-problem-detail.png)

## 原因未查明与其他结果 {#other-tiers}

**原因未查明**：AI 没能确认原因的用例。有这一档的用例时才列出，默认展开——没查明的差异里可能就有代码问题。标着「AI 推断，未核实」的标题只是 AI 的推测，只能当作排查线索。展开一条，能看到原因（如「同一个 SKU 的 available 由 12 变为 11。本次发布里没有找到与库存计算有关的代码改动，现有数据不足以确定原因。」）、「未查明的部分」、带来的差异（可点「查看差异」细看）、「AI 详查 N 条」的核对范围、「分析依据」和「查看 AI 分析过程」入口。分析还没轮到的用例也归在这一档，标明「其余 N 条排队中」「N 条还没分析」，或「N 条 AI 未得出结论」及原因。

排查有了结论之后：是代码问题的，修正代码后重新回放；确认差异可以接受的，在「查看 N 条用例」的抽屉里逐条标记通过；也可以点「重新分析」，让 AI 对着最新的代码再查一次。

**其他结果**：AI 已经查明、确认不是代码改动造成的用例（还没查明的在「原因未查明」）。这一档在界面上的其它叫法——节标题旁的「未测出需开发处理的问题」、接口表和导出文件里的「未测出新版本的问题」——都指它。默认收起成一行（「其他结果（N 条用例）」）；里面有要勾选忽略的噪音字段时默认展开。点开后一个结论一节，灰条写明为什么不算问题（页面不直接显示归类名，按下表对号入座）：

| 归类 | 为什么不算问题 |
|---|---|
| 疑似噪音 | 差异来自每次请求都会变的字段，判断为噪音 |
| 配置问题 | 差异与配置有关，未计入代码改动问题 |
| 回放失败 | 回放没跑成，未产生比对结果 |
| Softprobe 问题 | 问题出在 Softprobe 工具，与被测代码无关 |
| 录制不适用于新版本 | 旧录制不适用于新版本，本次未比成 |

其中「录制不适用于新版本」要单独说一句：差异的原因是代码改动，但新代码走了录制里没有的路，回放没有完成比对，这些接口的行为本次没有验证。它无须人工处理——录制由 Agent 自动进行，新版本运行、接口有请求进入后，后续回放自动使用新录制。

另外两类的处理方向：「配置问题」调整配置后重新回放；「回放失败」先检查被测服务，恢复后重新回放——它的说明里写明这些接口本次未验证。「回放失败」一节在带有代表用例（挑出来作样本的一条）时附「查看日志」入口。各节行尾都有「查看 N 条用例」和「查看 AI 分析过程」。这一档不需要开发处理，没有整组的「标记通过」，单条用例仍可在抽屉里标记。

疑似噪音的字段在这里勾选忽略，与 [按差异查看](#by-diff) 里的是同一套操作。

## 按差异查看 {#by-diff}

「按原因」是处理问题的主线；点问题区右上角的「按差异」，可以换一个角度核对：每一类差异被 AI 归到了哪里。切过去之后，页面上这一区域的标题变为「差异」。同一个字段或同一种报错的差异算一类，按类型分组——差异明细（接口返回的字段差异）、下游调用差异（对数据库、Redis、下游接口的调用与录制时不一致）、回放失败、疑似噪音，为空的分组不出现。没有 AI 分析结果时（没分析或服务端版本较旧），报告只有这一种列法。

「差异明细」这一组的行上标有去向：「已归入问题 01」「已归入其他结果」或「原因未查明」，与「按原因」里的问题一一对应。「疑似噪音」组的字段有三个来源：AI 分析原因判为噪音的字段；AI 降噪判断像噪音、但没有自动忽略的字段；这次回放没有降噪结果时，按字段名和取值形态推测的字段（如时间戳、编号、线程名）。

![按差异查看](/img/docs/testing/zh/report-by-diff.png)

字段行带勾选框。勾选一个或多个字段后，底部操作条提供两档忽略：

- **仅本次忽略**：只对这次回放生效；
- **永久忽略（N 项）**：写入应用的 [对比规则](/zh/testing/compare-rules-web-ui)，以后每次回放都不再比较。

勾选父路径会连带它下面的全部子路径，页面会列出连带的影响。忽略只是写好规则，这次回放的结果不变；按成功提示点「立即重新对比」，重新比对后相关用例才转为通过（界面上的「确认后忽略，相关用例转为通过」是省略的说法）。

## 回放设置与统计 {#replay-info}

「回放设置与统计」在报告底部，默认收起。展开后包括：

- **这次回放的设置**：回放目标地址（旁边注明发起人）、流量来源（录制时间段、全部接口或选定接口）、下游处理、用时。「下游处理」显示「返回值固定为录制时的原样」时，数据库、Redis、HTTP、系统时间都使用录制时的值；显示「真实调用下游」时，真的访问这些依赖。
- **未通过的接口**：每个接口的回放、通过、未通过条数；有分析结果时，未通过按三档拆开显示，如「9（代码改动引起 9）」，点「查看用例」转到用例列表。全部通过的接口收成一句，如「其余 1 个接口的 6 条用例全部通过」。
- **三步流程**：回放、AI 降噪、AI 分析原因各自的状态和用时，例如「忽略 1 类噪音后，15 个用例转为通过」。回放完成后，可在此「开始降噪」「分析本次回放」，或「重新降噪」「重新分析」。右下角的「流程设置」见 [流程设置](#flow-settings)。
- **已忽略的噪音**：见下。
- **代码版本**：AI 分析时读取的分支和提交，如「分析读的是 release/2.4 · 7c1e2ab（2026-09-29 10:34）」。Softprobe 不核对这个版本与被测服务实际运行的代码是否一致，页面注明「这次回放的服务是不是同一份代码，没有核对」。没绑代码仓库或没有分析时，显示「分析所用的代码版本没有记录」。

![展开后的回放设置与统计](/img/docs/testing/zh/report-info.png)

### 已忽略的噪音 {#ignored-noise}

这次回放中有被忽略的差异时，「回放设置与统计」里会出现「已忽略的噪音」。标题行是汇总，如「AI 自动忽略 1 类，仅本次回放生效 · 15 条用例因此通过 · 忽略规则跳过了 3 类差异，共 59 次」。展开后是两类行：

- **AI 自动忽略的字段**：一行一个字段，带 AI 给出的理由，只在本次回放中忽略。行尾有「永久忽略」和「撤销」：「永久忽略」把该字段写入应用的 [对比规则](/zh/testing/compare-rules-web-ui)（可选整个应用或仅该接口），之后每次回放都不再比较；「撤销」让它重新参与比对。AI 不会自行修改对比规则，永久忽略只能人工操作。
- **被对比规则跳过的差异**：标有「已配置的规则」，并显示跳过的次数。AI 自动忽略的字段也会按规则在这里再出现一次，所以同一个字段可能列出两行，汇总里「忽略规则跳过了 N 类差异」也把它算在内。

导出的「总览」里，这类差异是另一个口径，如「已配置规则忽略的差异（不计入结果）2 类，至少涉及 22 条用例」：不含 AI 自动忽略的字段，按涉及的用例数写，与页面汇总的「3 类差异，共 59 次」不矛盾。

![已忽略的噪音](/img/docs/testing/zh/report-ignored-noise.png)

## 流程设置 {#flow-settings}

在「回放设置与统计」的三步流程右下方点「流程设置」。设置对整个应用生效，从下一次回放开始起作用，不影响已完成的回放；已完成的回放如需补做，可在三步流程中手动开始。

![流程设置](/img/docs/testing/zh/report-flow-settings.png)

| 设置项 | 默认值 | 说明 |
|---|---|---|
| 回放结束后自动降噪 | 开启 | |
| 每日降噪次数上限 | 50 | 设为 0 则不再自动降噪 |
| 降噪使用的模型 | 默认模型 | 只列出已接入的可用模型 |
| 降噪完成后自动分析原因：CI 触发的回放 | 开启 | |
| 降噪完成后自动分析原因：手工回放 | 关闭 | 关闭时，需在报告中点击「分析本次回放」 |
| 每日自动分析次数上限 | 10 | 手动开始的分析不计入；设为 0 则不再自动分析 |
| 分析使用的模型 | 默认模型 | 只列出已接入、使用自己凭据的模型 |

此外：

- 降噪和分析两组设置分别保存。
- 降噪和分析都在服务端执行，使用这里设置的模型，与对话框里选择的模型无关。
- 接入模型、绑定代码仓库的方法见 [配置 AI 诊断与代码仓库](/zh/testing/installation/ai-diagnosis)。

## 导出报告 {#export-report}

需要归档、汇报或发到群里时，点页面头部的「导出」。

![导出菜单](/img/docs/testing/zh/report-export-menu.png)

| 菜单项 | 内容 | 适合 |
|---|---|---|
| 下载 Excel | 可筛选的 .xlsx，每行可点回平台 | 归档、逐条核对 |
| 打印 / 存 PDF | A4 固定版式，在打印窗口中选择「另存为 PDF」 | 汇报 |
| 复制摘要 | 结论和影响最大的前 5 条待确认差异，附完整报告链接；同时提供纯文本和富文本 | 群聊、邮件 |
| 复制 Markdown | 含表格的报告，包括结论、问题、差异和接口统计，不含逐条用例 | 工单、文档 |
| 复制链接 | 当前页面地址，含筛选条件 | 发给同事查看 |

回放进行中或排队中时，「下载 Excel」和「打印 / 存 PDF」不可用（显示「回放结束后可导出」）；三个复制项可以使用，内容按当时的进度写。

### Excel 内容 {#excel}

Excel 包含 5 张表：总览、待确认差异、已忽略的差异、接口明细、用例明细；有 AI 分析记录时增加「问题」表，共 6 张。

| 工作表 | 内容 |
|---|---|
| 总览 | 结论、统计数字、本次回放的设置和这份导出覆盖的范围。结论按用例数写，措辞与页面主句不同，如「13 条由代码改动引起，需开发确认或修正，3 条未测出新版本的问题，另有 1 条原因未查明」 |
| 问题 | AI 分析出的问题，与报告中的卡片一一对应；「核对」一列写「AI 核对通过」「AI 推断，未核实」或「按报错判定」。被并入的问题跟在它所并入的问题下面一行，不单独计数 |
| 待确认差异 | 按影响的用例数排序，每行附平台链接 |
| 已忽略的差异 | 忽略来源（AI 降噪或忽略规则）、理由、生效范围、当前是否仍生效 |
| 接口明细 | 每个接口的通过、有差异、回放失败条数 |
| 用例明细 | 默认只包含有差异和回放失败的用例；勾选菜单底部的「Excel 含通过的用例」后包含全部用例，最多 20,000 条 |

::: tip 数据不全时会注明
差异过多只列出影响最大的一部分、部分用例未能获取、用例数与统计数不一致时，「总览」中都会注明。有用例未能获取时，页面上还会出现提示，可点「重新导出」。
:::

![Excel 的总览表](/img/docs/testing/zh/report-export-excel.png)

### 打印版 {#print}

打印版为 A4 固定版式，主要包括结论、回放信息、问题（有 AI 分析时；三档都会列出，各带档名，如「代码改动：」「原因未查明：」「其他结果 · 疑似噪音：」）、待确认差异（只列前 20 条，其余提示到平台查看）、已忽略的差异、有问题的接口，以及这份导出覆盖的范围。逐条用例明细只在 Excel 中提供。
